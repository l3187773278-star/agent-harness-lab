# ADR-0002：为什么重试放在协议层（provider.js）

- 状态：已接受
- 日期：2026-10-03

## 背景

模型 API 会限流（429）、会 5xx、会超时、会断流。重试逻辑放在哪里，
决定了循环层（loop.js）写起来有多复杂。

## 决策

重试、退避、超时**全部**放在 `provider.js`，`loop.js` 完全不感知重试。
`provider.chat()` 要么返回一个完整结果，要么抛出"重试后仍失败"的
`ProviderError`。

## 理由

1. **决策循环不该做 I/O 策略**：loop 的职责是"根据结果决定下一步"。
   如果 loop 里散落着重试逻辑，每一步都要处理"这次是网络失败还是模型拒绝"，
   状态机会爆炸。
2. **重试语义因错误而异**：429 和 503 值得退避重试；400（参数错）重试
   只会重复同样的错；401（鉴权）重试无意义。这个分类知识属于协议层。
3. **可测试**：重试策略可以用假 fetch 单测（`test/provider.test.js` 里
   429→成功、503 全败、400 不重试三种场景），不用真网络。

## 细节

- 指数退避 + 25% 抖动：抖动是为了避免多任务同时重试撞上第二次限流。
- `Retry-After` 头暂未支持（v1 简化），已在代码注释中标注。
- 重试次数与每次退避时长都记入轨迹，进评测报告。
