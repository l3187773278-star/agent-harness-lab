# ADR-0004：上下文压缩——什么能压、什么不能压

- 状态：已接受
- 日期：2026-10-03

## 背景

长任务的对话历史迟早撞上窗口上限。压缩是必须的，但压缩错了比不压缩更糟：
丢关键信息会让模型开始胡猜，而且胡猜的样子往往很自信。

## 决策

压缩规则**写死成显式分类**，而不是交给模型自己总结：

| 内容 | 处理 | 理由 |
| --- | --- | --- |
| system 提示 | 永不压 | 稳定前缀 = prompt cache 锚点（实测缓存命中 90%+） |
| 用户任务描述 | 永不压 | 丢了它模型就不知道要干什么 |
| 最近 N 条消息 | 先保留 | 当前推理的直接上下文 |
| 旧工具结果 | 先压（截断到固定长度） | 体积最大、价值随时间衰减最快 |
| 旧 assistant 长篇正文 | 次压 | 结论重要，推导过程不重要 |
| reasoning（思维链） | 永远不回灌 | DeepSeek 文档明确要求多轮不回传；回传浪费 token 且干扰推理 |

## 渐进压缩

`buildRequestMessages` 不是一步压到最狠，而是分轮加压：
先压工具结果，再逐步收紧"保留最近消息"的条数（下限 2，至少保住最近一轮问答）。
只在需要时付出代价。

## 一个容易踩的坑（已写进代码注释）

压缩不能把一条 assistant 的 `tool_calls` 和它对应的 `tool` 结果拆开。
拆开会产生"孤立的 tool 结果"，在 OpenAI 兼容协议里是**非法消息序列**，
服务端直接报错。压缩边界遇到 `tool` 消息要回退到上一个 assistant 消息。
