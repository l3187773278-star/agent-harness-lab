# ADR-0003：token 估算为什么用字符启发式

- 状态：已接受（待真实数据校准）
- 日期：2026-10-03

## 背景

上下文预算判断（要不要压缩历史）发生在**调用之前**。真正的 token 数只有
调用后才知道。零依赖约束又排除了 tiktoken 之类的库。

## 决策

`src/tokens.js` 用字符启发式估算：ASCII 约 4 字符/token，非 ASCII（CJK）
约 1 字符/token，另加每条消息固定开销，并**刻意向上取整高估**。

## 理由

估算永远有误差。两个方向的误差代价不对称：

- **低估**：以为放得下，实际撞窗口 → 服务端拒绝 → 要么任务失败，
  要么被迫中途压缩（丢上下文）。
- **高估**：提前一点压缩 → 只是多压掉一些低价值历史，代价小。

所以宁可高估。`calibrationError()` 会在每次真实调用后记录"估算 vs 实际"，
评测报告里回填校准数据，这是"先用启发式跑起来，再拿真实数据修正"的常规做法。

## 已知局限

- 没有处理特殊 token（如代码里的长标识符会被高估）。
- 高估比例越大，压缩触发越早。校准数据的用途就是把这个比例调小。
