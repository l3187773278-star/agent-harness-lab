# ADR-0005：判分为什么用"留出测试"，而不是模型互评

- 状态：已接受
- 日期：2026-10-03

## 背景

评测 Agent 任务完成度有两个主流方案：

1. **模型互评**：让另一个大模型给 Agent 的结果打分（LLM-as-a-judge）。
2. **留出测试**：每个任务自带一套 Agent 看不到的自动测试，跑通了就是通过。

## 决策

判分全部用留出测试（`node --test` 跑评分器），**不用模型互评**。

## 理由

1. **确定性**：同一份结果在同一台机器上判分结果永远一样。互评模型
   有随机性，同一个答案两次打分可能不同 —— 评测报告的数字必须可复现。
2. **无法作弊**：评分器在 Agent 跑完之后才注入工作区，Agent 改不了判分逻辑；
   而且评分器是纯代码，Agent 就算"说服"自己完成了任务，测试不通过就是不通过。
3. **成本与速度**：互评要为每个任务再花一次模型调用；测试判分是免费的。
4. **评判标准可审计**：测试就是标准本身，写在仓库里谁都能看。互评的
   打分理由藏在 prompt 里，很难审计。

## 代价

留出测试只能测"能自动判定的任务"（代码修复、算法正确性），测不了
"生成的文案好不好"这类主观任务。这是本评测集的边界，已在 SPEC 里写明：
数字的意义在于可复现，不在于覆盖面。

## 建设过程中的一个教训

任务建设时发现：**评分器必须经过"双向验证"** —— 种子 bug 实现必须被抓住
（否则任务没难度），参考正确实现必须通过（否则评分器误判）。
这个验证做成了 `bench/reference-solutions.mjs`，是评测集质量的门禁。
